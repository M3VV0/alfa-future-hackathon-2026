# ADR-0002: единственный клиентский вход — веб-интерфейс

Дата: 20.10.2026. Статус: принято по уточнению пользователя.

## Решение

Клиент использует только веб-кабинет на Thymeleaf + HTMX. Отдельного публичного JSON API, SDK и маршрутов `/api/v1/**` для клиентских операций в MVP нет. Это уточняет прежнее разделение MVC и JSON API в ADR-0001 и архитектуре до версии 1.3.

Цепочка вызова: браузер → Nginx → MVC-контроллер → application service → доменная логика / хранилища / задания. Контроллер вызывает Java service напрямую, без внутреннего HTTP-вызова самого себя. У каждой бизнес-команды один web-маршрут.

## Маршруты и представления

- Страницы, формы и HTMX-фрагменты находятся в `/app/**`; вход — `GET/POST /login`, выход — `POST /logout`.
- Формы отправляются как `application/x-www-form-urlencoded`, документы — `multipart/form-data`. Скачивание возвращает содержимое файла с соответствующим MIME.
- Например, `POST /app/applications/{id}/submit` отправляет заявку и ставит задачу. Отдельного JSON-варианта этой команды нет.
- Обычный успешный POST возвращает `303 Location` на страницу результата. HTMX получает HTML-фрагмент или указание навигации через `HX-Redirect`; успешный частичный ответ имеет статус 200.
- Если один GET возвращает страницу или фрагмент, представление выбирается по `HX-Request`. Контракт указывает заголовок, MIME и допустимые ответы. Приватные страницы не должны кэшироваться как публичные; при кэшировании вариантов нужен `Vary: HX-Request`.
- Статус: `GET /app/applications/{id}/status` возвращает HTML-карточку этапа, следующего действия и результата; HTMX обновляет её каждые 2-5 секунд до завершения обработки. Это вспомогательное представление существующего состояния, а не второй способ отправить заявку.

## Безопасность, повторы и ошибки

Сессия и CSRF остаются в Spring Security / Spring Session JDBC. Обычная форма передаёт `_csrf`, HTMX — CSRF в заголовке. Право на компанию и каждый объект проверяется на сервере.

Оптимистическая блокировка использует скрытое поле `version` в форме. Для повторяемых команд форма получает скрытый `command_id`: двойное нажатие и повтор после потери ответа с тем же ключом дают один бизнес-эффект. Новый payload с тем же ключом возвращает конфликт. Эти поля проверяются сервером и не заменяют авторизацию. При ошибке валидации после исправления данных формируется новый command_id; при повторе сетевого запроса прежний ключ сохраняется.

Неправильные поля возвращают HTML-форму с ошибками, статус 422; HTMX настраивается на отображение такого ответа. Конфликт версии — 409 с объяснением и действием обновления; права/CSRF — 403; неизвестный объект — 404; временная ошибка — 503. Истёкшая сессия приводит к странице входа; для HTMX используется навигация всего окна, чтобы форма входа не вставилась в карточку статуса. Все технические ответы содержат безопасный trace_id для диагностики.

## Внутренние API

JSON API сохраняются для service-to-service взаимодействия: assessment `/request`, получение результата `/requests/{request_id}`, callback `/internal/processed` и локальные моки. Их используют workers и технические интеграционные проверки. Nginx клиентского контура не публикует эти маршруты; service credentials отделены от браузерной сессии.

Клиент не управляет статусом заявки или джобой через технический API. Изменения происходят через web-команды и фоновые обработчики. Следовательно, ограничение «веб — единственный клиентский вход» совместимо с внутренними API и асинхронной архитектурой.

## API-документация по ТЗ

Требование OpenAPI/Swagger и коллекции запросов сохраняется. Документируется существующий HTTP-контракт; ради Swagger дополнительный JSON API не создаётся.

- `openapi/web.yaml`: web-маршруты, form-urlencoded/multipart, session-cookie, CSRF, command_id/version, ответы text/html, файлы, redirects и заголовки HTMX. Спецификация ведётся явно; нельзя полагаться на автоматическое включение всех Thymeleaf MVC-контроллеров в springdoc.
- `openapi/internal.yaml`: JSON-контракты assessment/callback/моков и service auth. Springdoc используется для внутренних REST-контроллеров; экспорт сверяется с версионированной спецификацией.
- Swagger UI позволяет просмотреть спецификации и контракты. Коллекция технической проверки выполняет реальные web-запросы: читает login-форму и CSRF, сохраняет cookie и command_id, отправляет формы, проверяет HTML, статусы и redirects. Внутренние запросы исполняются из локальной сети стенда с отдельными credentials.
- Основной пользовательский сценарий эксперты проходят в работающем веб-интерфейсе. Swagger и коллекция — инструменты технической проверки, а не отдельный клиентский канал.

OpenAPI допускает разные media types и form/multipart-запросы. Это позволяет выполнить требования к документации без выделенного клиентского REST API. Эти файлы — план реализации; текущий ADR их не создаёт.

## Последствия

Убираются дубли MVC/REST-контроллеров, клиентские JSON DTO и переговоры о JSON/HTML-представлении одной команды. Сохраняются Java application services, доменные проверки и внутренние контракты. Проект становится проще в объёме выбранного web-only MVP. Публичный интеграционный API потребует отдельного будущего решения и не считается частью текущего плана.
