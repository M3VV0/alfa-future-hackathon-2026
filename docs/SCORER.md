# Обмен Java backend со скорером

Реализованы отправка `POST /request` во внешний сервис и приём результата на `POST /scored` в Java backend. Python-модель и сервер скорера этим изменением не реализуются. Контракт в формате OpenAPI: [openapi/scorer.yaml](openapi/scorer.yaml).

## Запрос в скорер

```http
POST http://localhost:8000/request
Content-Type: application/json
X-Scorer-Token: <SCORER_TOKEN>
```

```json
{
  "id": "a051d4c4-6f76-4a56-a181-1ddcc6821177",
  "parameters": {
    "requested_amount": "1000000.50",
    "currency": "RUB",
    "term_months": 24,
    "payment_frequency": "monthly",
    "financing_purpose": "equipment",
    "declared_collateral_value": null,
    "applicant_entity_type": "legal_entity",
    "applicant_inn": "7700000000",
    "msp_category": "micro",
    "snapshot_on": "2026-10-25",
    "average_headcount": 10
  }
}
```

`id` — UUID существующей заявки. `parameters` — вход для `Scorer.predict`, без `id` и `target`. Поля имеют имена и значения категорий из [контракта модели](../code/scorer/docs/INTERFACE.md). Параметры заявки объединяются с сохранёнными сведениями `Business`, включая доступные реестровые и вложенные данные. Суммы передаются точными десятичными строками в рублях; модель поддерживает такой ввод. Даты — строки `YYYY-MM-DD`. `snapshot_on` — дата создания заявки в UTC.

Неизвестные сведения передаются как `null`, а не заменяются выдуманными значениями. Например, `msp_category` может отсутствовать в существующем профиле компании: текущая заглушка решения может принять такой запрос, но перед реальным `predict` обязательные поля модели нужно заполнить или вернуть техническую ошибку. Обогащение данных в эту интеграцию не входит.

Скорер должен сохранять запрос и возвращать **`202 Accepted` после commit**, не ожидая `predict` и отправки callback. В своей БД скорер может хранить `id`, `status`, `payload JSONB`, `created_at`, счётчик попыток и время следующего выполнения. Его асинхронный worker подбирает сохранённое задание, вызывает модель и отправляет результат в Java backend.

Повторный запрос с тем же `id` и теми же параметрами должен быть идемпотентным: вернуть `202`, не создавать ещё одно задание; при готовом результате можно повторить callback. Если параметры для того же `id` отличаются, скорер должен вернуть `409`. Это обязательное условие повторов после сетевой ошибки или перезапуска Java backend.

## Callback в Java backend

Скорер обращается по настроенному у него адресу Java backend, например:

```http
POST http://localhost:8080/scored
Content-Type: application/json
X-Scorer-Token: <SCORER_TOKEN>
```

Пока кредитное решение не реализовано, скорер может отправлять заглушку с отказом:

```json
{
  "status": "DECLINED",
  "months": null,
  "percent": null,
  "sum": null,
  "id": "a051d4c4-6f76-4a56-a181-1ddcc6821177"
}
```

Для отказа также допустимы нулевые значения условий. Java сохраняет полученный результат; отказ не подменяется технической ошибкой.

| Поле | Формат |
| --- | --- |
| `id` | Обязательный UUID отправленной заявки |
| `status` | Обязательное значение `OK`, `DECLINED` или `OFFER` |
| `months` | Целое неотрицательное число месяцев; для `OK` и `OFFER` обязательно и больше нуля |
| `percent` | Неотрицательная годовая ставка в процентах: `15.5` означает 15,5%; до 5 цифр до точки и 4 после; обязательно для `OK` и `OFFER` |
| `sum` | Неотрицательная сумма в рублях, до 15 цифр до точки и 2 после; для `OK` и `OFFER` обязательна и больше нуля |

| HTTP | Значение |
| --- | --- |
| `204` | Результат сохранён либо идентичный результат уже был принят |
| `400` | Некорректный JSON, статус или условия |
| `401` | Отсутствует или неверен служебный токен; пустой токен в конфигурации также запрещает callback |
| `404` | Заявка не найдена |
| `409` | Заявка ещё не отправлялась либо для неё уже сохранён другой результат |

Для чисел сравниваются значения, а не количество десятичных знаков: `15` и `15.0000` считаются одинаковыми. При повторном callback время первого результата сохраняется. Конфликтующий ответ не перезаписывает результат. Поздний ответ для отправленного задания принимается даже после технического таймаута.

Callback использует отдельную цепочку Spring Security только для `POST /scored`. Она требует служебный токен, не требует браузерный JWT или CSRF и не меняет защиту клиентских POST-запросов. Токен не записывается в журнал.

## Сохранение и исполнение в Java

- Новая заявка, снимок запроса и `CreditApplicationTask` сохраняются в одной транзакции. Снимок не меняется при редактировании компании и повторных отправках.
- Миграция `V5` добавляет в задание `requestPayload JSONB`, `attempts`, `nextAttemptAt`, `updatedAt`, `lastError` и терминальные статусы `COMPLETED` / `FAILED`. Существующие задания сохраняются; для заданий без снимка он создаётся при первой отправке из текущих сведений компании.
- Worker берёт одно готовое задание через `FOR UPDATE SKIP LOCKED`, сохраняет `PROCESSING` и время окончания аренды. После завершения транзакции выполняет HTTP-запрос.
- После `202` задание переходит в `AWAITING_RESULT`. При временной ошибке снова становится `PENDING`. Просроченные `PROCESSING` и `AWAITING_RESULT` подбираются повторно, в том числе после перезапуска процесса.
- Сетевые ошибки, неожиданный ACK, `5xx`, `408` и `429` допускают повтор. Остальные `4xx` завершают задание технической ошибкой. Число отправок ограничено.
- После исчерпания попыток заявка и задание получают `FAILED`. Причина сохраняется безопасным кодом, без содержимого запроса и токена.
- Принятый callback атомарно сохраняет `CreditApplication.scoredResult JSONB`, `scoredAt` и переводит заявку и задание в `COMPLETED`. Бизнес-результат находится в `scoredResult.status`, например `DECLINED`.
- Быстрый callback, полученный до `202`, и ответ старой попытки не могут вернуть завершённую заявку в ожидание. Блокировки БД не удерживаются во время HTTP-запроса.

## Конфигурация и запуск

Worker по умолчанию выключен. Для включения нужны адрес скорера и общий служебный токен.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `SCORER_ENABLED` | `false` | Включить Java worker отправки |
| `SCORER_BASE_URL` | `http://localhost:8000` | Адрес сервиса скорера |
| `SCORER_TOKEN` | Пусто | Общий токен заголовка `X-Scorer-Token`; обязателен при включённом worker |
| `SCORER_CONNECT_TIMEOUT` | `PT3S` | Таймаут соединения |
| `SCORER_READ_TIMEOUT` | `PT10S` | Таймаут HTTP-ответа |
| `SCORER_REQUEST_LEASE` | `PT30S` | Аренда отправляемого задания; выбирайте больше суммарных HTTP-таймаутов |
| `SCORER_CALLBACK_TIMEOUT` | `PT60S` | Время ожидания результата после ACK |
| `SCORER_RETRY_DELAY` | `PT5S` | Задержка перед повтором после временной ошибки |
| `SCORER_MAX_ATTEMPTS` | `5` | Максимальное число отправок одного снимка |
| `SCORER_POLL_DELAY_MS` | `1000` | Пауза между выборками заданий |
| `SCORER_INITIAL_DELAY_MS` | `1000` | Задержка первого запуска worker |

Например, из корня репозитория, с уже запущенным сервисом скорера:

```sh
POSTGRES_PORT=5433 docker compose --project-name smartcreditor-dev up -d --wait
cd code/app/backend
SPRING_PROFILES_ACTIVE=dev \
DB_URL=jdbc:postgresql://localhost:5433/smartcreditor \
SCORER_ENABLED=true \
SCORER_BASE_URL=http://localhost:8000 \
SCORER_TOKEN=local-scorer-demo-token \
sh ./mvnw spring-boot:run
```

При запуске `main` этой версии веб-шаблонов и автоматических демо-аккаунтов нет: интеграция основана на `751972c`, без изменений ветки `frontend`. Пользователь, компания и права на неё должны существовать до подачи заявки. Для ручной имитации ответа используйте `curl` с UUID уже отправленной заявки и тем же `SCORER_TOKEN`:

```sh
curl -i http://localhost:8080/scored \
  -H 'Content-Type: application/json' \
  -H 'X-Scorer-Token: local-scorer-demo-token' \
  --data '{"status":"DECLINED","months":null,"percent":null,"sum":null,"id":"a051d4c4-6f76-4a56-a181-1ddcc6821177"}'
```

## Проверки

При запущенном PostgreSQL выполните из `code/app/backend`:

```sh
SPRING_PROFILES_ACTIVE=dev \
DB_URL=jdbc:postgresql://localhost:5433/smartcreditor \
sh ./mvnw test
```

HTTP-тесты поднимают локальную заглушку `/request`. Интеграционные тесты используют отдельную временную схему PostgreSQL и удаляют только эту схему; реальные задания разработки не подбираются тестовым worker. Покрыты снимок данных и точные суммы, callback с отказом до ACK, дубли и конфликты, служебная авторизация и CSRF клиентского маршрута, временные и постоянные ошибки, таймаут callback, поздний ответ, восстановление зависшего задания и конкурирующие workers.
